# 今後の作業整理

## 目的

この TodoList カレンダーアプリを、今後の機能追加に耐えられる状態へ整える。

まずは既存コードをリファクタリングし、現在の中心機能である「タスクの本当に残っている残り時間を表示する」体験を壊さずに、Google カレンダー同期やプロジェクト機能を追加しやすい構造にする。

## 優先順位

1. リファクタリング
2. Google カレンダー同期の調査
3. Google カレンダー同期の実装
4. プロジェクト機能の設計
5. プロジェクト機能の実装

## フェーズ1: リファクタリング

昔作ったコードを、今後の拡張に耐えられる形へ整理する。

主に見るべき観点は以下。

- `app/page.tsx` に集まっている状態管理やモーダル制御を整理する
- Firebase との読み書き処理を UI コンポーネントから分離する
- 予定、タスク、一時タスク、設定のデータ取得・保存処理を見通しよくする
- 猶予時間やカレンダー表示の計算ロジックをテストしやすい純粋関数に寄せる
- 巨大化しているコンポーネントを、責務ごとに分割する
- `console.log`、命名ミス、不要なコメント、重複処理を減らす
- TypeScript の型を整理し、Firestore の保存形式とアプリ内の型を区別できるようにする

このフェーズでは大きな機能追加はせず、既存の動作を保ったまま構造を改善する。

## フェーズ2: Google カレンダー同期の調査

Google カレンダー同期は、実装前に仕様と制約を確認する。

同期対象はスケジュール（予定）のみとする。タスクは Google カレンダーへ同期せず、このアプリ内で統一して管理する。

調査すべきことは以下。

- Google Calendar API で何ができるか
- OAuth 認証を Next.js と Firebase の構成でどう扱うか
- 既存の `schedules` データと Google カレンダーのイベントデータをどう対応させるか
- `tasks` は同期対象外とし、Google カレンダーイベントと混ぜずに扱う設計にする
- 同期方向をどうするか
- 繰り返し予定をどう扱うか
- Google 側で削除・変更された予定をどう反映するか
- アプリ側で削除・変更された予定を Google 側へどう反映するか
- 重複作成をどう防ぐか
- 同期失敗時にユーザーへどう見せるか

最初から完全な双方向同期を目指すのではなく、まずは実現可能性と安全な最小実装を確認する。

## フェーズ3: Google カレンダー同期の実装

調査結果に基づいて、段階的に実装する。

最初の実装候補は以下。

- Google カレンダーから予定を読み込むだけの片方向同期
- アプリ内の予定と Google イベントの対応 ID を保存する
- タスクは同期処理に含めず、既存のタスク管理と猶予時間計算はアプリ内データを使い続ける
- 手動同期ボタンを用意し、自動同期は後回しにする
- 同期対象カレンダーをユーザーが選べるようにする
- 同期ログやエラーを最低限確認できるようにする

片方向同期でデータ構造と UX が安定してから、双方向同期や自動同期を検討する。

## フェーズ4: プロジェクト機能の設計

README に書かれている「タスクを入れ子構造で管理し、タスクの分割をサポートする」機能を具体化する。

設計時に決めるべきことは以下。

- プロジェクトとタスクの関係
- タスクの親子構造を何階層まで許可するか
- 親タスクの所要時間を子タスクから自動計算するか
- 親タスクの締切を子タスクへ継承するか
- プロジェクト単位で猶予時間を表示するか
- 既存タスクをプロジェクトへ移動できるようにするか
- カレンダー、タスクリスト、詳細編集 UI でどう表示するか

この段階では、いきなり実装せず、まずデータ構造と画面上の扱いを固める。

## フェーズ5: プロジェクト機能の実装

設計が固まったら、小さく実装する。

最初の実装候補は以下。

- プロジェクトの作成、編集、削除
- タスクをプロジェクトに紐づける
- タスクリストでプロジェクトごとに表示する
- プロジェクト内のタスク合計時間を表示する
- 既存タスクの猶予時間計算を壊さない

タスクの入れ子や高度な集計は、基本的なプロジェクト管理が動いてから追加する。

## 直近の次アクション

まずはリファクタリングのために、現在のコードを以下の順番で確認する。

1. 主要なデータ型を確認する
2. Firebase の読み書き箇所を洗い出す
3. カレンダー表示と猶予時間計算のロジックを確認する
4. 大きすぎるコンポーネントを特定する
5. 既存動作を壊さないための最低限の確認手順を決める
6. 小さい単位でリファクタリングを進める

最初のリファクタリング対象としては、`useEvents` 周辺のデータ取得処理と、猶予時間計算ロジックの整理が優先度高め。
